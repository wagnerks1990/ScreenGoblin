# ScreenGoblin pre-production implementation audit

**Review date:** 2026-09-11  
**Scope:** Current prototype architecture/schema/contracts, the project handoff, and Brand Package v1. This is an implementation gate, not a legal certification or a claim that ScreenGoblin is an emergency-notification system.

## Verdict

**Not ready for a pre-production pilot yet.** The concept and ADR establish the correct high-level boundaries—organization scoping, unique device credentials, complete-manifest activation, last-known-good playback, expiring commands, and explicit emergency expiry—but the current data model does not yet enforce several of them. The P0 gates below must pass before a school network or real screen is connected.

The highest-risk omissions are:

1. no first-class draft/review/approve/publish/rollback lifecycle;
2. organization-wide roles without building/location scope or separate emergency/device-control permissions;
3. bearer-style device enrollment without proof-of-possession, rotation, replay protection, or attestation state;
4. emergency records without approval, acknowledgement, delivery/render status, or safe partial-failure handling;
5. no modeled device-command, immutable manifest release, content-version, or update-ring workflow;
6. no defined privacy/retention policy for screenshots, audit data, integrations, or possible student information;
7. no measurable offline, recovery, supply-chain, deployment, or accessibility release gates.

## What the prototype should preserve

- Keep the three-product separation: Console, API, and Player.
- Keep deterministic scheduling and make AI advisory only; AI must never publish, clear an alert, or operate devices autonomously.
- Keep player connections outbound-only and capability-based across Android TV, managed AOSP, and Amazon Signage.
- Keep precise operational copy. The mascot belongs in onboarding and empty/success states, not outages, alerts, dense tables, or security errors.
- Keep `brand-tokens.json` as the visual source of truth, but validate rendered combinations rather than assuming named brand colors are accessible.

## Emergency publishing acceptance checklist

All items are P0 for enabling the feature in a school pilot.

- [ ] Emergency capability is behind a feature flag and is clearly labeled **supplemental**, with documented independent life-safety channels.
- [ ] Dedicated emergency permission is separate from normal publish, organization admin, and device admin permissions.
- [ ] Publisher performs step-up MFA. District-wide or other policy-defined scopes require a different authorized approver; break-glass use is narrowly scoped, immediately alerted, and post-reviewed.
- [ ] Only locked, accessibility-reviewed templates may be used. Editable fields have length/character/contrast limits and a mandatory expiry; AI cannot write, approve, send, extend, or clear an alert.
- [ ] Confirmation shows the exact message preview, target snapshot, timezone, start/expiry, online/offline/unsupported/excluded device counts, initiator, approver, and reason.
- [ ] Activation and clear are signed, expiring, idempotent commands. Replays, reordered messages, duplicate pushes, and stale commands are rejected.
- [ ] Player acknowledges at least `received`, `assets_verified`, `activated`, `first_frame_rendered`, `expired/cleared`, and `normal_programming_restored`; failures retain actionable reason codes.
- [ ] Console displays partial delivery in real time and triggers an out-of-band escalation when a defined success threshold/deadline is missed.
- [ ] Push failure is recovered by bounded polling. A disconnected player locally expires the alert at its signed deadline; a late/reconnected player never activates an already-expired alert.
- [ ] Power loss, process death, corrupted cache, full disk, incorrect wall clock, timezone/DST change, server loss, and rollback during an alert have passing physical-device tests.
- [ ] Clearing an alert restores a previously verified normal release atomically. If unavailable, a neutral locally bundled fallback appears—never a blank screen or stale alert.
- [ ] A test/drill mode is visually distinct and cannot be mistaken for a live emergency. Production targets cannot be selected from non-production environments.
- [ ] The append-only audit record and export reconstruct who authored, approved, sent, received, rendered, failed, cleared, and reviewed the event.

## Pre-production release gates

### Gate A — Product and data model

- [ ] Versioned migrations create first-class organizations, scoped permissions, locations, screen groups, immutable assets/releases/manifests, approvals, commands, acknowledgements, device credentials, update rings, and retention records.
- [ ] Publish preview resolves a target snapshot and effective schedule; approval and publish are separate actions with optimistic concurrency protection.
- [ ] Rollback restores a known release without mutating history; deleting referenced media cannot break a published or rollback release.
- [ ] At least two organizations and three location scopes are used in automated isolation tests.
- [ ] Decommission/re-enrollment, user disablement, role change, ownership transfer, and lost-device workflows are exercised end to end.

### Gate B — API, web, and media security

- [ ] Threat model covers Console, API, worker, object storage/CDN, Player, push channel, third-party integrations, CI/CD, and administrator/support access.
- [ ] API meets an agreed OWASP ASVS 5.0 level—use Level 2 as the prototype baseline—and maps test evidence to requirements ([OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)).
- [ ] Automated tests cover broken object/function authorization, mass assignment, pagination/export leakage, replay, rate limits, WebSocket isolation, SSRF, malicious upload/polyglot/decompression bomb, stored XSS, CSRF, and signed-URL expiry.
- [ ] Production headers/CSP, cookie settings, CORS allowlist, body/upload limits, request timeouts, dependency error redaction, and generic authentication errors are verified from a deployed environment.
- [ ] Password/session/device/pairing secrets never appear in client bundles, database dumps, traces, screenshots, analytics, or logs.
- [ ] Independent dynamic and manual security review has no unresolved critical/high issue; medium issues have named owners and deadlines.

### Gate C — Android player and fleet reliability

- [ ] Release build passes the OWASP MASVS areas relevant to ScreenGoblin: storage, cryptography, authentication, network, platform, code, resilience, and privacy ([OWASP MASVS](https://mas.owasp.org/MASVS/)).
- [ ] Release manifest exports only required Android components; custom IPC requires signature-level permission or is not exported; backups/debugging/cleartext are disabled as appropriate.
- [ ] Unique non-exportable player key, enrollment confirmation, credential rotation/revocation, and replay-resistant request authentication pass on each supported hardware class.
- [ ] Atomic two-slot cache survives forced power loss at every update phase. Hash/signature mismatch, missing asset, unsupported codec, full disk, and render crash keep or restore known-good content.
- [ ] Player remains useful through the declared offline support window; cache eviction cannot remove active/rollback/emergency-fallback assets.
- [ ] Boot, watchdog, process update, OS update, factory reset, HDMI reconnect, display power cycle, 24-hour soak, and repeated network flap tests pass on emulator, Onn 4K Pro, a direct-install TV, Amazon Signage Stick, and the chosen managed AOSP target before claiming those devices are supported.
- [ ] Capability matrix is versioned and the Console never offers an unsupported command as if it will work.
- [ ] Accessibility/service interaction, overscan/safe area, 1080p/4K, landscape/portrait, D-pad escape, kiosk breakout, and audio behavior are physically tested.

### Gate D — Privacy and school readiness

- [ ] Approved data-flow inventory identifies every collected field, source, purpose, legal/contractual basis, recipient/subprocessor, location, retention period, and deletion method.
- [ ] District can deploy a no-student-PII profile; sample/demo data contains no real people; logs and screenshots have short documented retention and least-privilege access.
- [ ] FERPA/COPPA and applicable Pennsylvania/district policy review is completed by the responsible school/privacy counsel; contracts prohibit advertising, behavioral profiling, unrelated reuse, and unauthorized sale/disclosure.
- [ ] Camera, microphone, audience analytics, face recognition, precise location, advertising ID, and third-party marketing analytics are absent or build-time disabled—not merely hidden in the UI.
- [ ] Privacy request, legal hold, tenant export, tenant deletion, breach response, and lost-player procedures have named owners and tabletop evidence.
- [ ] Public screens have a content policy for names/photos, accessibility, QR destinations, copyright/licensing, expiration, and prohibited sensitive information.

### Gate E — Supply chain and deployment

- [ ] Protected branches require review and passing tests; CI uses least-privilege, short-lived credentials; untrusted pull requests cannot access production/signing secrets.
- [ ] Dependencies/actions/base images are version- or digest-pinned with automated update review, license policy, secret scanning, SAST, dependency/container/IaC scanning, and a documented vulnerability SLA.
- [ ] Each web/API/container/APK release has an SBOM, checksum, signature, source revision, build provenance, migration version, and immutable artifact retention. NIST SSDF calls for release integrity/provenance and vulnerability response ([NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final)); CISA defines minimum SBOM elements ([CISA 2025 SBOM Minimum Elements](https://www.cisa.gov/sites/default/files/2025-08/2025_CISA_SBOM_Minimum_Elements.pdf)); SLSA provenance links artifacts to their build/source ([SLSA provenance](https://slsa.dev/spec/v1.2/provenance)).
- [ ] Production containers run non-root with read-only filesystem where practical, dropped capabilities, health/readiness checks, resource limits, isolated networks, and pinned images; database/object storage are not publicly reachable.
- [ ] Dev/staging/production tenants, databases, buckets, keys, push topics, domains, and device enrollment are separated. Production rejects artifacts/configuration signed by non-production roots.
- [ ] Deployment supports backward-compatible migration, canary/update rings, health-based halt, and tested rollback. Player promotion is `development -> lab -> pilot -> general`, with minimum soak and explicit human approval.
- [ ] Signing-key loss/compromise, dependency compromise, malicious release, expired certificate, backend outage, corrupt backup, and mass bad-command scenarios have runbooks and completed tabletop tests.

### Gate F — Operability and launch decision

- [ ] Service-level indicators exist for API availability/latency/errors, queue age, manifest generation, object delivery, player connection/sync/render state, emergency acknowledgement, notification delivery, and audit-pipeline health.
- [ ] Alerts are actionable, deduplicated, severity-ranked, and routed to named responders; dashboards expose tenant-safe aggregate health without high-cardinality PII.
- [ ] Support can diagnose common failures without remote shell or unrestricted access; every support impersonation/access event requires consent, scope, expiry, and audit.
- [ ] Backup restore, regional/site outage, certificate rotation, database migration rollback, and player fleet rollback rehearsals meet approved RPO/RTO.
- [ ] Accessibility, security, privacy, emergency, and device-matrix evidence is attached to a signed go/no-go record. Any waived gate names the owner, rationale, compensating control, and expiry date.

## Minimum pilot definition

A defensible pre-production prototype is a **non-life-safety, non-PII pilot** on a dedicated signage VLAN with test content and a small device ring. Emergency publishing, SIS/Schoology imports, public QR analytics, support shell, and district-wide mass actions should remain disabled until their respective P0/P1 gates pass. The pilot succeeds only if it demonstrates tenant isolation, scoped approvals, immutable publishing, device credential lifecycle, atomic offline playback, safe rollback, observable delivery/render state, accessible Console operation, and reproducible signed releases.
